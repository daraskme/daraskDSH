# MiniMax H3 ネイティブ化計画の敵対的レビュー（gpt-6.2-astra、dsh ask openai 経由）

**最初に着手すべきは専用ワーカーではなく、既存ワークフローでの再計測です。** 1280×704×121 は参照実装では 124 フレーム相当に切り上がり、映像だけで 32,560 token あります。また、49 秒から 30 秒を切るには、GEMM だけでなくデコード・保存側からも秒単位で削る必要があります。

1. **［高］27k token を前提にした FLOP 見積もりは過小。** `nodes_minimax_h3.py:50–63` では 121 → 124 フレーム → 潜在時間長 37。映像は `37 × 22 × 40 = 32,560` 行、音声はさらに 414 行、その後にテキスト分を足します。実チェックポイントの投影形状で数えると、50 ブロックの QKV・出力投影・MLP だけで **約 1.27 PFLOP/forward**（テキスト抜き、FMA＝2）。dense attention は約 1.56 PFLOP、単純にその 10% としても約 0.156 PFLOP です。  
   **最小修正:** 計測した `PackedLayout.seq_len` と実フレーム数を表に載せ、1.05 PFLOP・250 TFLOPS は差し替える。尺を変えてよい場合だけ、次の短い格子点 **107 フレーム**を候補にする。121 → 120 では計算は減りません。

2. **［高］SLA は「全 attention の時間が 10%」ではなく、モデル単体の計測では経路ごと変わる。** 保存済みグラフは全期間・`min_tokens=0`・`extra_tokens=0`・`exact_kv_and_rows`。10% は選択するキーブロックの割合で、対角・条件 KV・音声の dense 行、選択・パックの時間は残ります。H3 専用経路は BF16 活性を条件に、QKV を 4,096 行ずつ投影して `sol_attn_chunked` に渡します。パッチを外して測れば別の GEMM 形状になり、dense に落ちればスコア・値積の演算量は概ね一桁増えます。  
   **最小修正:** 単体計測スクリプトを削り、実グラフで sparse producer の発火とカーネル時間を確認する。`model.py:185–197` の Q/K RMSNorm＋RoPE は既に融合済みなので、「要素演算合計が10%なら融合を追加」も削る。

3. **［致命］30 秒の完了条件に対し、FP8 に要求している利得が大きすぎる。** サンプリング以外が現状の約 11 秒なら、38 秒を **19 秒以下**にする必要があります。仮にサンプリング時間の 80% が FP8 対象で、そこだけ実効 2 倍になっても、全体は `11 + 38 × (0.2 + 0.8/2) = 33.8 秒`。しかもこれは活性変換まで含めて 2 倍という仮定です。  
   **最小修正:** 30 秒は FP8 の合格条件ではなく、デコード・保存も含めた目標にする。実グラフで FP8 後の残り秒数を出し、専用化に進む前に、その不足を埋める処理を特定する。

4. **［高］`fp8_e4m3fn_fast` を選ぶだけでは「LoRA をマージして一度だけ量子化」の実験にならない。** ローカルの `comfy/ops.py:951–1009` の fast 経路は scale が 1 で、活性を呼び出しごとに ±448 に clamp して cast します。重みパッチの状態や例外によっては通常の linear に戻ります。小さな LoRA 差分が丸めで消えるリスクもあります。Anima の学習全体の 4% は転用できませんが、**forward 単独でも**量子化込みでは形状によって BF16 より遅かった点は直接参考になります。  
   **最小修正:** 同じ BF16 ベースに強度 1 の LoRA を高精度で一度反映し、BF16 対照とそこから量子化した DiT を比較する。Qwen の int8 convrot と SLA 内部の int8 は変更せず、FP8 GEMM の発火・変換込みの秒数・LoRA の効きと映像／音声を確認する。PSNR を採否基準にしない。

5. **［高］10.3 秒を「Conv3d の VAE」とみなすと、約 2 割の区間を丸ごと取り逃がす。** `minimax/vae.py` の 3D CNN は主に**エンコーダー**で、動画**デコーダーは ViT3D**。現グラフの末尾には映像 VAE のほかに音声 VAE、動画作成、MP4 保存があります。Conv3d の設定を変えても、ViT・転送・エンコードが占める秒数は縮まりません。  
   **最小修正:** 手順5を専用化より前へ移し、同じ生成済み latent で映像 decode・音声 decode・MP4 保存を分けて測る。`channels_last → cuDNN → BF16` の試行列は削り、保存が重ければ同等画質のハードウェアエンコード、映像 decode が重ければ実際の ViT 演算を先に見る。

6. **［高］固定シードの反復は、推論ではなく ComfyUI のノードキャッシュを測り得る。** 同じグラフ・プロンプト・シードをそのまま再送すると、サンプラーまで再利用されても「依頼から完了」は短くなります。逆に「初回 15 秒」が大条件のロード込み総時間なら、現状ではロードをゼロにしても warm の約 49 秒が残ります。  
   **最小修正:** 速度用はあらかじめ選んだ異なる 3 シードを旧・新で共用し、各回 8 step と音声付き MP4 の新規保存を確認する。品質用は旧・新で同一シード。「初回15秒」は解像度と起点を明記できなければ削除する。

7. **［高］常駐化で 2 回目以降の 40 秒は削れない。現行経路でも既に払っていない。** 小条件で観測された cold と warm の差は約 36 秒。常駐 71 GB に Gemma 20 GB を足すと名目の余裕は約 5 GB、学習 17 GB でも約 8 GB しかなく、ピーク次第で OOM です。ロックは実行を直列化しても、別プロセスに残った重みを解放しません。退避すれば次の H3 は完全な warm ではありません。  
   **最小修正:** 新しいキューと統一ロックは先に作らず、既存の排他下で **H3 → 他ジョブ → H3** を一往復だけ測る。引き渡し時の実 VRAM と復帰後の MP4 完成時間で常駐の採否を決める。

8. **［高］`comfy/ldm/minimax` の部分移植は、速くならないまま映像・音声の互換性を壊し得る。** SLA のブロック置換は `comfy_extras`、AV の時間格子・条件付け・SigmaShift もモデル本体の外です。DiT だけ一致しても、音声スケジュールや sparse の条件行が違えば別の出力になります。また GPL コードを組み込んだ派生物を配布する場合、移植行へのライセンス表記だけでは足りません。  
   **最小修正:** まず既存 ComfyUI 経路のまま速度を詰め、チャット／サイドバーはその経路を呼ぶ。部分コピーと P-H3 共通化は今回から削除。旧グラフは、代替経路で速度・映像・音声を比較し終えるまで削除しない。

**判定：要修正。既存ワークフロー上の計測からのみ着手可。**

## 第 2 回レビュー（完全ネイティブ版の計画に対して）

1. **［致命］SLA は「CUDA ソースをビルドする」だけではネイティブから呼べない。**  
   **失敗:** 現行の comfy-kitchen 0.2.41 の wheel には SM 12.0 用の Sol producer が入っている。問題は GPU の非対応ではない。[上流の CMake](https://github.com/Comfy-Org/comfy-kitchen/blob/v0.2.41/comfy_kitchen/backends/cuda/CMakeLists.txt) は CUDA 12.8 以上を要求し、標準の成果物は Python/nanobind モジュール `_C`。逆に `sol_attn.cu` 一枚だけ抜いても、producer・route・exact などが揃わない。DiT 移植後にこれが判明すると、長尺を dense でしか動かせない。  
   **最小修正:** 既存グラフの計測直後に、0.2.41 固定で Sol が使う翻訳単位・ヘッダーだけを組み、対象 LibTorch の CUDA stream 上で **SM 12.0・実形状の 1 ブロック**を動かす。wheel のロードや全バックエンドの移植はしない。

2. **［高］サンプラーの仕様参照先が違い、特に音声を壊す。**  
   **失敗:** `comfy/ldm/minimax/sampling.py` は **画像版の PDD 用**。動画の実グラフは `BasicGuider` の正条件のみ、`simple` の 8 step。10 と 3 は単一の shift 値ではなく映像・音声それぞれの shift で、サンプラーは映像側の sigma で両方を運ぶ。DiT に入る音声と、戻る音声速度に別々の変換があるため、sigma 列だけ合わせても映像は出るのに音声が崩れ得る。  
   **最小修正:** `model_sampling.py:338–357`、`model_base.py:2230–2252`、`minimax/model.py:673–714` を動画の仕様にする。旧グラフの **9 個の sigma** と、中間 step での映像・音声それぞれの DiT 入力・速度・denoised を照合する。画像版 PDD と負条件の forward は削る。

3. **［高］`sol_attn` 一回と、現行グラフの `sol_attn_chunked` は同じ経路ではない。**  
   **失敗:** 実装は T2V の `[text | audio | video]` 順で、映像開始前までを含む 64 行ブロックの KV を常に残し、音声を含む query ブロックを dense にする。さらに BF16 QKV を 4,096 行ずつ渡し、各層の初回だけ統計取得と量子化の二巡、以後は前 step の `kmean/vscale` を使う。単純な「全行 top 10%」は音声・条件を変え、毎 step の二巡は QKV 投影を余分に繰り返す。  
   **最小修正:** `nodes_sparse_attention.py:84–100,248–307` と kitchen 側の top-k 閾値計算までを固定仕様にする。同じブロックの**初回と次 step**で、sink 範囲・統計・出力を比較する。今のグラフにない VSA や汎用パッチ機構は移植しない。

4. **［高］テキスト条件の終点が Qwen 出力になっており、実 LoRA の対象が漏れる。**  
   **失敗:** 実ファイル `H3_VBVR_Pro-V2` の対象は 208 投影。50 ブロックの 200 投影のほか、**2 層の token refiner に 8 投影**ある。本体だけマージするとロードは成功しても条件が違う。また通常の Qwen チャットテンプレートや最終 RMSNorm を使うと、refiner より前から不一致になる。  
   **最小修正:** H3 の生プロンプトの **token ID 列（完全一致、T2V のタグは全て 1）→ 第50層の未正規化出力 5120 次元 → `condition_proj`＋LoRA 適用済み refiner の出力 5376 次元**の順に照合する。最後の条件は `model_base.py:2254–2261` どおり生成ごとに一度だけ作る。vision・参照入力・P-H3 共通化は削る。

5. **［高］int8 convrot の BF16 復元は、単なる cast でも、短文なら安い処理でもない。**  
   **失敗:** 実重みの言語部は 350 投影が group 256 の回転済み int8、scale は出力行ごと。`int8 × scale` だけでは回転した基底のままになる。正しく逆回転しても、層ごとに BF16 を実体化すれば新規プロンプトごとに約 **48.8 GB の重みを書き出す**。また BF16 GEMM は現行の活性量子化を含む int8 演算と数値的に同一ではない。  
   **最小修正:** 正しい行 scale＋逆回転による層単位 BF16 を初版にするなら、1 投影で復元を確認した上で、旧 int8 との第50層出力の差と**新規プロンプト**の時間を測る。「速度への影響は小さい」と「差は BF16 丸め」の前提を削り、許容できなければ現行相当の int8 演算を使う。

6. **［高］「DiT 1 forward、サンプラー 1 step」では、移植の誤りを見逃す。**  
   **失敗:** `res_multistep` は初回と終端が Euler、中間だけが前回の denoised を使う二次更新（`k_diffusion/sampling.py:1485–1528`）。全 step を Euler にしても初回比較は通る。また旧 `RandomNoise` は CPU の同じ生成器から映像→音声の順に別々に `randn` するため、同じ seed で CUDA 上に一括生成しても同じ入力にはならない。  
   **最小修正:** 手順1で短尺一件の旧グラフから AV noise・条件・中間 latent を採り、各部品へ直接入力する。照合順は **1 ブロック → 1 forward の AV 両出力 → 初回・履歴を使う第2回・終端の更新**。注入値で合った後、seed からの通し生成でも確認する。全モデルの FP32 対照は不要。

7. **［高］VAE 本体の出力一致だけでは、保存される映像・音声は一致しない。**  
   **失敗:** 使用中の dully fp16 は `decoder.transformer_blocks` 型で、潜在の逆正規化、空間タイル、時間チャンクの重なり・切り詰めまでが動画 decode。単純な ViT 一括実行では継ぎ目・尺・ピーク VRAM が変わる。音声も `audio_vae.py` の外で `VAEDecodeAudio` が波形を `max(1, 5×std)` で割り、保存側が映像尺で音声末尾を切る。ここを飛ばすと VAE が一致しても音量・末尾が違う。  
   **最小修正:** 同一の最終 AV latent から、**圧縮前の RGB と音量補正後の 32 kHz ステレオ波形**を先に比較し、長尺 MP4 は 124 フレーム・24 fps・音声末尾を確認する。VAE エンコーダーと全フレームの MP4 間 PSNR は削る。

8. **［中］FP8 は BF16 一致後で正しい。ただしパネル実装後まで待つ理由はない。**  
   **失敗:** FP8 投影の出力を FP8 のまま SLA に渡すと、現行 producer の BF16 入力契約を外れ、失敗または dense 化する。GEMM 単体が速くても総時間は悪化し得る。また 49 秒→35 秒には 14 秒の短縮が必要で、対象部分が変換込みでちょうど 2 倍になるとしても、元の対象時間が **28 秒以上**なければ届かない。  
   **最小修正:** ネイティブ BF16 で音声付き MP4 が一致した直後、UI 統合前に、同じマージ済み重みから DiT の投影だけを FP8 化する。**BF16 出力で同じ SLA producer が発火することと、変換込みの総秒数**で採否を決める。「約34秒が上限」は完了条件から削る。

**判定：要修正。旧グラフの計測と SM 12.0 のネイティブ SLA 確認からは着手可。**

補足（同じ回の短い返答）:
先のレビューの判定に変更はありません。指摘 3 の照合点は、**token ID 列（完全一致）→ Qwen の未正規化出力（各トークン 5120 次元）→ LoRA 適用済み refiner の出力（5376 次元）**です。最後のテンソルは各 step で作り直さず、1 回の生成につき一度だけ計算します。
