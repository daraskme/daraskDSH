# Anima ネイティブ学習 実測結果

対象: RTX PRO 6000 Blackwell Workstation Edition（SM 12.0, 600 W 上限, クロック非固定）、1 画像、batch 1、rank 16、BF16、AdamW (optimi 互換)。step 時間はウォームアップ後の中央値。

## 構成比較（ms/step）

| 構成 | 512px | 1024px | ピーク VRAM (512 / 1024) |
|---|---:|---:|---|
| diffusion-pipe（activation checkpointing あり＝現行既定） | 316 | 439 | — |
| diffusion-pipe（checkpointing なし） | 205 | 340 | — |
| 最小 PyTorch ループ eager | 135 | 292 | 8.6 / 21.9 GiB |
| 最小 PyTorch ループ compile (Inductor) | 82–86 | **222** | 7.0 / 15.7 GiB |
| **ネイティブ C++/CUDA（現行）** | **78** | 249–263 | 8.6 / 21.9 GiB |

- diffusion-pipe と eager/compile/native は 2026-11-18 の計測（`.runtime/anima-bench-l99erh95`）。native は 2026-11-20 に再計測（512: 77.7 ms、1024: 248.5 ms）。
- 1024px ではコンパイル版がネイティブより約 12% 速い。差は要素ごとの演算の融合で、言語の差ではない。

## 手順 1: step の内訳（2026-11-20, ネイティブ, `torch.profiler` CUDA トレース）

`nsys` が未導入のため、CUPTI のカーネル時間で集計した。プロファイラ有効時は起動ごとの負荷で壁時計が延びるので、壁時計は非計測時の値を使う。

| | 512px | 1024px |
|---|---:|---:|
| 壁時計 / step（非計測時） | 77.7 ms | 248.5 ms |
| GPU 稼働時間 / step | 64.6 ms | 247.6 ms |
| **GPU 空白** | **約 13 ms（17%）** | **ほぼ 0** |
| カーネル起動数 / step | 10,690 | 10,605 |
| GEMM | 36.3 ms（4,068 回） | 111.8 ms |
| attention（FlashAttention-2 系） | 6.6 ms | 51.0 ms（backward 36.6 ms） |
| 要素ごとの演算・その他 | 8.4 ms（2,888 回） | 42.9 ms |
| **コピー・型変換** | **9.7 ms（2,804 回）** | **32.5 ms** |
| reduce・norm | 3.4 ms | 9.0 ms |
| オプティマイザー | 0.4 ms | 0.5 ms |
| memcpy | 1.5 ms | 2.8 ms |

### 読み取り

- **GEMM 以外が GPU 時間の約 1/3（512: 21.5 ms、1024: 84 ms）。** 最大の削減対象。コピー・型変換が 1 step で 2,800 回起動されており、計画の手順 2（重複 cast の除去）が直接効く。
- **CUDA Graphs の上限は 512px で約 13 ms、1024px ではほぼ 0。** 起動数を減らせばこの空白も縮むので、Graphs は手順 2 と融合の後に再判定する。
- **1024px の attention backward（36.6 ms）が単一カーネルとして最大。** PyTorch 同梱の FlashAttention-2（sm80 系）で動いている。cuDNN SDPA との比較（手順 6）は 1024px では優先度を上げる価値がある。
- GEMM は cuBLAS の `cutlass_80` 系 (mma.sync) カーネル。SM 12.0 には wgmma/tcgen05 がないので想定どおり。
- LoRA の小行列（wmma 16x16 / 32x32）は 896 回・約 5.5 ms（512px）。

## 手順 2: 重複 cast の除去（2026-11-20）

変更（`model.cpp`）: `linear` は凍結 W と LoRA A で 1 回の cast を共有する。self-attention の Q/K/V は FP32 入力を 1 回だけ BF16 にする。全ブロックの adaLN が読む timestep 埋め込みは最初に 1 回だけ cast する。

| | 512px | 1024px |
|---|---:|---:|
| ms/step（前 → 後、非計測時） | 77.7 → **73.9（−5%）** | 248.5 → **238.7（−4%）** |
| コピー・型変換 / step | 9.7 → 7.9 ms | 32.5 → 27.0 ms |
| カーネル起動数 / step | 10,690 → 10,130 | 10,605 → 10,045 |

品質:
- 順伝播は参照と一致（相対誤差 0）。
- LoRA 勾配全体: 参照との相対 L2 0.0063、コサイン 0.99998、ノルム比 0.99999。
- 層ごとでは、勾配が小さく打ち消し合いの大きい adaLN 層で最大 14.5% の差。BF16 で勾配の和を取る順序が変わったため。FP32 で計算した参照と比べると、参照の BF16 自体が全体で 25.5% ずれており、ネイティブも 25.5%（層ごとの誤差合計は +0.45%）。BF16 由来の誤差の範囲内と判断した。
- 1024px・200 step の loss 曲線: 20 step ごとの平均の差は ±1.6% 以内。全体平均は 0.001902 → 0.001896。
- `tests/model_parity.py` の BF16 判定を、層ごとの 1e-5 から「全体の相対 L2 ≤ 0.02、コサイン ≥ 0.9999、ノルム比 ±1%」に変更した。CPU の FP32 モデルでは引き続き層ごとに 1e-5 で判定する。

残るコピー・型変換（約 2,200 回）の主な発生源は、RMSNorm と LayerNorm の FP32 往復、RoPE の `cat`、attention 前後の転置コピー。cast の削除では減らせず、融合の対象になる。

## 手順 3: batch>1（2026-11-20）

同じ画像を B 枚に並べてエンジンに渡して計測した（エンジンは `[B,16,1,H,W]` に対応済み。Rust の前処理はまだ B=1 だけを作る）。別プロセスが VRAM を約 30 GB 使っている状態で計測した。

| | B=1 | B=2 | B=4 | B=8 |
|---|---:|---:|---:|---:|
| 512px ms/step | 77.4 | 113.4 | 226.6 | 437.7 |
| 512px **ms/枚** | 77.4 | **56.7（−27%）** | 56.6 | 54.7 |
| 512px ピーク VRAM | 8.4 GiB | 12.8 | 21.6 | 39.3 |
| 1024px ms/枚 | 239.2 | 248.0（+4%） | VRAM 不足 | — |

- 1024px はすでに GPU 律速なので、batch を増やしても速くならない。512px は B=2 でほぼ上限に達する。

品質（代理指標）: 1 画像で学習し、固定した 64 組の noise・timestep で denoising loss を評価した。値は未学習ベースからの改善率。

| 条件 | 学習時間 | 改善率 |
|---|---:|---:|
| B=1 × 400 step, lr 2e-5（400 枚分） | 33.6 s | 70.7% |
| B=2 × 200 step, lr 2e-5（400 枚分） | 28.2 s | 64.2% |
| B=2 × 200 step, lr 4e-5（400 枚分） | 28.0 s | 67.3% |
| B=1 × 290 step, lr 2e-5（同じ時間） | 25.0 s | 65.3% |
| **B=2 × 145 step, lr 4e-5（同じ時間）** | **20.1 s** | **68.2%** |

- 同じ枚数で比べると B=2 は学習が少し浅い。
- 同じ時間で比べると、B=2・lr×2 は B=1 と同等以上の改善率を約 20% 短い時間で出す。
- 単一画像の代理指標なので、ばらつきは ±2〜3 ポイントある。複数画像・アスペクト比混在のデータセットでは、同じバケットの画像が揃わない分だけ利得が下がる。

採用（2026-11-20）: `standalone.cpp` で、パッチ数 1,280 以下（約 572px 以下）の同じ形状のサンプルを、シードで並べ替えてから 2 枚ずつ組にする。エンジンは step ごとに `lr × B` を使う。`--epochs` の step 数は組分け後のバッチ数から C++ 側で数える（ABI 2）。端数と大きい画像は B=1。CLI では 4 枚 2 epoch → 4 step、3 枚 → 2 step、1024px → B=1、`--steps` 指定はそのまま、を確認した。

## 手順 4: 凍結 QKV / cross KV の連結（2026-11-20、不採用）

凍結された self Q/K/V と cross K/V の重みをロード時に連結し、1 回の GEMM で計算してから分割した。LoRA A/B は投影ごとに独立のまま。

| | 512px | 1024px |
|---|---:|---:|
| 連結前（手順 2 後） | 73.9 ms | 238.7 ms |
| 連結後 | 74.3–74.9 ms | 236.8–246.8 ms |

- 速くならなかった。この形状の GEMM はすでに計算律速で、呼び出し回数を減らしても時間は縮まない。
- BF16 では cuBLAS のカーネル選択と縮約順が変わり、予測が参照から 0.65% ずれた。勾配は参照とのコサインが 0.977 まで下がった（FP32 では 2e-7 で一致し、計算式自体は正しい）。
- 計画の規則（速くならなければ捨てる）に従い、元に戻した。

## 手順 6: attention の方式比較（2026-11-20、変更なし）

実際の形状（BF16、16 ヘッド × 128 次元、モデルと同じ転置レイアウト）で、forward と backward の合計時間を比べた。PyTorch 2.9.1 + cu128、cuDNN 9.10.2。

| 形状 | flash（自動選択） | cuDNN | efficient |
|---|---:|---:|---:|
| 512 self B=1 | 0.159 ms | 0.158 | 0.550 |
| 512 self B=2 | 0.240 | 0.222 | 0.924 |
| 512 cross B=2 | 0.139 | 0.149 | 0.531 |
| 1024 self | **1.474** | 1.643 | 6.621 |
| 1024 cross | **0.257** | 0.279 | 1.022 |

- 自動選択（FlashAttention-2）がすでに最速か同等。cuDNN が勝つのは 512px の self B=2 だけで、1 step あたり 0.5 ms にとどまるので固定しない。
- 1024px の self-attention は約 480 GFLOP を 1.47 ms で処理しており、約 330 TFLOPS 出ている。SM 12.0 向けのより速い attention 実装は手軽には手に入らない。

## 要素ごとの演算の融合（2026-11-20、採用）

計画 v2 にはなかった追加項目。1024px で GEMM と attention 以外にかかる時間（84 ms）を減らすため、次の 4 つを 1 つずつ入れて測った。

| 変更 | 内容 | 効果 |
|---|---|---|
| 融合 RMSNorm | q/k の RMSNorm を ATen の `at::rms_norm`（CUDA の融合カーネル）に置き換え | 1 回あたりの fwd+bwd が 0.316 → 0.060 ms。512px 73.9 → 62.5 ms、1024px 238.7 → 216.6 ms |
| `LoraLinear` | 独自の autograd 関数。LoRA 項を cuBLAS `addmm` の C 入力として渡し、forward の `base + B(Ax)` と backward の `dX_W + dX_A` を GEMM の中で足す | 1024px の GPU 稼働時間が 213.0 → 208.5 ms。起動数が 756 減 |
| 融合 RoPE | `rope.cu`（NVRTC → PTX）。回転ペアごとに 1 スレッドで、FP32 で計算して BF16 への丸めは 1 回。backward は転置回転 | 起動数が 448 減。GEMM と attention 以外の時間が小さく減少 |
| LayerNorm の affine に変調を統合 | `(1+scale)` と `shift` をサンプルごとに LayerNorm の weight と bias として渡す | 1024px で GEMM と attention 以外が 40.5 → 28.8 ms、GPU 稼働時間 213.5 → 195.6 ms。VRAM −1.3 GB |

融合後（非計測時）:

| | 開始時（手順 1） | 融合後 |
|---|---:|---:|
| 512px B=1 ms/step | 77.7 | 約 60–64 |
| 512px B=2 ms/枚（既定） | — | 約 55 |
| 1024px ms/step | 248.5 | **209.0**（compile は 222） |
| 1024px で GEMM と attention 以外の時間 | 84 ms | 28.8 ms |
| カーネル起動数 / step | 10,690 | 約 6,500 |

- 起動の負荷が減ったぶん、512px で B=2 にする利得は 1 枚あたり −27% から約 −8〜12% に縮んだ。それでも速いので B=2 は維持する。
- 画面表示に使われている同じ GPU で計測しているため、壁時計は 1 回ごとに ±3〜5 ms ぶれる。比較は CUPTI で測った GPU 稼働時間の A/B を優先した。

品質:
- 融合 RMSNorm、`LoraLinear`、融合 RoPE は、BF16 への丸めを参照（autocast）と異なる順序で行う。このため参照とビット一致はしなくなった（勾配のコサインは 0.989）。
- 代わりに `tests/bf16_accuracy.py` で、FP32 で計算した参照に対する誤差を参照の BF16 版と比べる。参照の BF16 版より 5% 以上悪ければ失敗とする。

| FP32 に対する誤差 | 参照 BF16 | ネイティブ（融合後） |
|---|---:|---:|
| 予測 | 0.01224 | 0.01217 |
| 勾配全体 | 0.2551 | **0.2279** |
| 層ごとの誤差の合計 | 376.6 | **264.9** |

- ネイティブのほうが FP32 に近い。丸めの回数が減ったため。
- 1024px・200 step の loss 曲線は、20 step ごとの平均の差が ±1.7% 以内。全体平均は 0.001902 → 0.001894。
- `tests/model_parity.py` の BF16 判定は、大きく外れていないかの確認（相対 L2 ≤ 0.2、コサイン ≥ 0.98、ノルム比 ±5%、予測 ≤ 0.02）に緩めた。CPU の FP32 は従来どおり 1e-5 で判定し、2〜4e-7 で通る。

## 手順 7: FP8 凍結 GEMM（2026-11-20、不採用）

`torch._scaled_mm`（cuBLASLt、SM 12.0）、per-tensor scale。重みは E4M3 でロード時に 1 回だけ量子化し、dX 用に転置コピーも持つ。活性と勾配は毎回 amax → scale → cast で量子化し、その時間も含めて測った。1024px の形状（4,096 トークン）、単位は ms。

| 形状 | BF16 fwd | FP8 fwd（GEMM のみ） | BF16 dX | FP8 dX（e5m2 / e4m3） |
|---|---:|---:|---:|---:|
| 2048×2048 | 0.145 | 0.110（0.071） | 0.126 | 0.123 / 0.122 |
| mlp1 2048→8192 | 0.422 | 0.327（0.251） | 0.410 | 0.453 / 0.514 |
| mlp2 8192→2048 | 0.474 | 0.487（0.245） | 0.421 | 0.306 / 0.309 |
| 512px B=2 mlp1 | 0.204 | 0.169（0.134） | 0.247 | 0.253 / 0.265 |

- GEMM だけなら 1.7〜1.9 倍速い。しかし量子化のカーネル 3 つが利得の大半を消し、forward は 1.0〜1.3 倍、dX は形状によって速くも遅くもなる。
- 凍結された forward GEMM をすべて FP8 にしても、1024px で約 8 ms/step（約 4%）にとどまる見込み。
- GEMM 1 回の相対誤差は約 3.8%（dX を e5m2 にすると 5.9%）。BF16 は約 0.3%。E4M3 の仮数部が 3 ビットしかないための誤差で、per-channel scale にしても減らない。28 ブロック分積み重なる。
- 計画の判定（量子化のコスト込みで勝たなければ打ち切る）に従い、打ち切った。
- 再検討の条件: 量子化を前段のカーネル（LayerNorm、GELU など）の出力に融合し、scale を前の step の値で決めれば、GEMM 単体の 1.7〜1.9 倍に近づく。それでも上限は 1024px で 1 step あたり約 25 ms（約 12%）。品質は ComfyUI での出力比較で判定する必要がある。

## 計画への反映

1. 手順 2（cast の重複除去）をそのまま次に実施する。コピー・型変換の 9.7 / 32.5 ms が対象。
2. 1024px は GPU 律速なので、Graphs より要素ごとの演算の融合と attention の比較を先に検討する。
3. 512px で Graphs を検討するのは、手順 2 の後に GPU 空白が 10% 以上残る場合だけ。

再計測: `.runtime/lora-venv/bin/python plugins/dsh-anima-lora-trainer/native/tests/profile_steps.py 512 40 <出力先>`（CUDA のみをトレースし、各 step の AdamW カーネルを区切りに 6 step 目以降を集計）。
