# H3 画像条件・チャット・リモート計画の敵対的レビュー（gpt-6.2-astra、OpenAI API 経由）

1. **H3 の重み選択（未確定①）**  
   **失敗**：Eros beta7 で動画が出ても、画像条件が効いた証拠にはならない。I2V 用の `fl2va` を ref2video の代替にするのも誤り。  
   **最小修正**：**Eros を先に試す。** 移植前に ComfyUI で seed・プロンプトを固定し、I2V は末尾画像だけ、ref2video は指定した参照画像だけを替えて追従を見る。失敗したモードだけ、I2V は `fl2va`＋`fl2v_turbo_8step`、ref2video は同梱テンプレートの `ref2va`＋`ref2v_turbo_4step` に切り替える。現行 native の疎注意 QKV と LoRA 合成は int8 ConvRot にそのまま使えないので、切替時だけ適用キー数と投影出力を照合する。

2. **P-H3 の ref 生成（未確定②）**  
   **失敗**：`subject_definitions:` は生成モードのスイッチではない。`PH3ImageConditioning` では `Edit <Picture 1>. ` の自動付与を止めるだけで、画像は編集時と同じ `minimax_refs` に入る。  
   **最小修正**：**拡張器も専用文法も移植しない。** P-H3 拡張器の実出力を一例だけ採り、その文面を直接渡す。参照の特徴を保ちつつ第1画像と異なる構図を作れ、参照差し替えにも追従した場合だけ、同じ編集経路の「ref 生成」プリセットとして出す。

3. **vision 重みと画像トークン列**  
   **失敗**：実重みは H3 が `visual.*`、P-H3 が `model.visual.*` で、視覚塔は両方とも **BF16**。P-H3 条件入力にチャットテンプレートもない。現行 `capture_reference.py` は画像を表す辞書を token ID の採取から落とすため、ID 一致だけでは画像の挿入ずれを見逃す。  
   **最小修正**：視覚塔は通常の PyTorch で読み、両モデルとも `<Picture n>: `＋vision ブロック＋本文を使う。異寸法の2枚で各画像の開始位置・長さ・grid、interleaved mRoPE の `position_ids` を保存する。deepstack のマスクは画像本体だけ、DiT の tag 0 は開始・終了トークン込みとして別々に照合する。

4. **リサイズ・末尾フレーム・乱数**  
   **失敗**：先頭だけの39フレーム試験では、先頭の stretch、末尾の中央 crop、末尾位置の取り違えを検出できない。H3 の `match` も出力寸法への引き伸ばしではなく、面積上限までの縮小＋各辺32丸め。  
   **最小修正**：縦横の異なる両端画像で「要求38 → 実39 → 末尾 index 38」を1件採る。P-H3 は大画像1枚から vision 用（100万画素上限）と VAE 用（出力面積、未指定時は `2912²`）を別採取する。VAE の H3＝mean、P-H3＝CPU seed 42 のサンプルと、DiT の **patchify 後に条件ごとにジョブ seed で再開**するノイズを混同しない。

5. **DiT の行境界と SLA**  
   **失敗**：`dit.cpp` は `audio_start=text_len` と仮定している。条件行を挿すと、SLA で厳密に扱う KV 範囲、密に計算する音声 query 範囲、出力ヘッドの切り出しがずれる。step 0 だけでは SLA 統計の引き継ぎも検証できない。  
   **最小修正**：実際の segments から両 target の開始位置を取り、KV は先頭から video 開始まで、dense query は audio 開始から video 開始までを64行境界に丸める。異寸法 ref で位置・変調区間・映像音声出力を step 0/1 で照合する。固定の layout・条件行はジョブ内で再利用し、対象外モードまで一般化しない。

6. **一致と速度の合格基準**  
   **失敗**：「既存 T2V/T2I は通しでビット一致」は基準にできない。既存記録では H3 は採取済み条件を注入すると一致するが、通しの最終 latent は相対32%差。P-H3 も同じ latent からの RGB は PSNR 60.5 dB で、画素一致ではない。  
   **最小修正**：整数の位置・タグと同一入力を注入した DiT は厳密照合、通しは固定 seed で参照への追従と画像なし経路の非退行を見る。速度は採取フックを外し、ロード込みの投入→保存と推論時間を分ける。全モードの二重測定より、通常尺・参照9枚で所要時間とピーク VRAM を1回測る。

7. **チャットと GPU キュー**  
   **失敗**：`jobs.mjs` の排他はプロセス内で、投入結果は自分の ID ではなく全ジョブの一覧。チャットから直接読み込んで無期限に待つと、別 worker の起動や切断後の二重投入を招く。ホスト側 worker にパスだけ渡すと、セッションの読取権限も引き継げない。  
   **最小修正**：Anima・P-H3・H3 と学習は Studio の既存キュー1個に集約する。チャットは許可済み入力をジョブに固定して固有 ID を受け取り、その ID だけ期限付きで待機・再照会・取消する。完了時はパスと Studio 内の結果リンクを返す。LLM ごとの実装は不要。

8. **リモート転送と LoRA 学習データ**  
   **失敗**：20 MiB の画像は base64 だけで約26.7 MiB。現行 API は本文を全量バッファし、動画 GET も全量を `200` で返す。さらに学習は既定で既存 `.txt` を上書きする。375 px の表示確認ではどれも発見できない。  
   **最小修正**：gateway は変えず、owner 限定で1ファイルずつ受け、受信量・画素数・合計量を制限する。学習は同名の画像と `.txt` を対にし、上書きは既定 OFF、再起動後の再実行まで原本を保持する。動画 GET は Range/206 に対応し、実機で Access 越しに「学習データ投入」と「生成動画の再生・シーク」を各1回通す。
