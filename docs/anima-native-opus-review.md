# Anima LoRA ネイティブ学習計画の設計レビュー

DeepSeek Harness、diffusion-pipe、Anima の実コードは `/tmp` にないため、このレビューは計画文と一般的な実装知識だけに基づいています。「要確認」と書いた箇所は、実装前にコードで確かめてください。

## 結論

C++/LibTorch を第一候補にする判断は不採用を推奨します。第一候補は「DeepSpeed を外した PyTorch 学習ループ」に置き換えます。このループには torch.compile、CUDA Graphs、SDPA、潜在表現とテキスト条件のキャッシュを入れます。ネイティブ化は、プロファイルでホスト側の律速が残ると確認できた場合だけ行う段階的な選択肢にします。

ただし、Python ランタイムを排除すること自体が要件なら、その要件を計画に明記してください。その場合は、速度ではなく配布要件として採否を決めることになります。

## 重大度順の修正事項

### 致命的：計画の方向を変えるもの

**1. 「言語による利得」はほぼ発生しない見込み**

LibTorch は PyTorch と同じ ATen、cuBLAS、cuDNN、Flash SDPA のカーネルを呼びます。概算は次のとおりです（要実測）。

- **前提（Cosmos Predict2 2B 相当）**
  - 28 ブロック、d=2048
  - 1024px では VAE で 1/8、パッチで 1/2 となり、4096 トークン
- **1024px の計算量**
  - 順伝播は線形層で約 16 TFLOP、self-attention で約 4 TFLOP
  - 重みが凍結されているので逆伝播は dX だけを計算し、約 26 TFLOP
  - 1 枚あたり合計約 45 TFLOP
  - 実効 200 TFLOPS と仮定すると約 0.2 s/枚
  - Python の起動オーバーヘッド（数千回のカーネル起動で 15〜50 ms）は 1 割未満で、CUDA Graphs を使えばさらに縮みます
- **512px・バッチ 1 の計算量**
  - 1 枚あたり約 9 TFLOP、約 45 ms
  - この条件だけは起動律速になり得ます
  - ただしバッチを増やすか、PyTorch 側で CUDA Graphs や `mode="reduce-overhead"` を使えば解消でき、C++ にする必要はありません

速度差の大半は次の要因から生まれます。いずれも言語とは関係ありません。

- 再計算（activation checkpointing）の除去：順伝播 1 回分、約 30% の削減
- DeepSpeed エンジンの除去
- attention バックエンドの選択
- 起動回数の削減

**2. C++ に移すと、かえって遅くなる経路を選ぶことになる**

- LibTorch からは Inductor（torch.compile）、Triton による自動融合、FlexAttention を使えません。融合はすべて手書きの CUDA になります。
- 計画にある「エクスポート」の経路は学習には使えません。TorchScript は保守モードです。torch.export と AOTInductor は推論向けで、C++ 側で逆伝播を回す用途は安定していません。
- したがって、選べる経路は手作業での移植だけです。自動微分は `torch::autograd` で得られますが、融合カーネルを入れるたびに独自の autograd Function と、その勾配検証が必要になります。
- 実行時の準備も軽くなりません。LibTorch の cu128 版も CUDA ライブラリ一式（数 GB）を含みます。さらに ABI と nvcc 12.8 以上の要件が加わります。

**3. 比較対象（ベースライン）の定義が不足しており、利得の帰属を誤る**

次の 4 つの構成を必須にしてください。

- (a) diffusion-pipe をそのまま
- (b) diffusion-pipe の設定を最適化したもの（再計算なし、キャッシュあり、SDPA を固定）
- (c) DeepSpeed を使わない最小の PyTorch ループ（eager と compile の 2 通り）
- (d) ネイティブ実装

「言語による利得」は (c) と (d) の差だけです。(a) との差を C++ の成果として扱ってはいけません。

### 高

**4. 初期 LoRA の B=0 のままでは勾配テストが無効になる**

標準的な初期化では B=0 なので、最初のステップでは dL/dA=0 となり、出力もベースモデルと一致します。この状態では A への勾配経路も LoRA の倍率も検証できません。

- 比較用には、A と B の両方を非ゼロの乱数で初期化した LoRA を使ってください。
- 「下流から上流まで届く」ことは、ゼロでないことの確認だけでは足りません。全ブロックについて、層ごとの LoRA 勾配ノルムを参照実装と比べてください。

**5. 正しさの判定基準（許容誤差）が未定義**

BF16 では、カーネルの選び方や縮約の順序が違うだけで、ビット単位の一致は得られません。次の 2 段階で判定してください。

- **FP32 での比較**
  - 小さい解像度と少ないブロック数で、両実装とも FP32 にし、決定的アルゴリズムを使い、TF32 を無効にします
  - 予測、損失、勾配の相対誤差が 1e-5 程度であることを確認します
- **BF16 での比較**
  - 勾配のコサイン類似度が 0.999 以上で、相対ノルム誤差が数 % 以内であることを確認します
  - N ステップの損失曲線が、シード固定の参照実装と許容範囲内に収まることを確認します

さらに、ネイティブ側は参照実装が書き出したキャッシュ（latent、テキスト条件、noise、timestep）をそのまま読み込むようにします。こうすると、比較から乱数生成と前処理の差が取り除かれます。

**6. Blackwell の SM 12.0 は SM 10.0（B200）とは別物**

- **使えないもの**
  - SM 12.0 には tcgen05、TMEM、wgmma がありません
  - そのため FA3（Hopper 専用）、FA4（SM 10.0 向け）、CUTLASS の SM100 向けサンプルは動きません
- **共有メモリの制約**
  - SM あたりの共有メモリは Hopper より小さくなっています
  - Hopper 向けのタイル設定や Triton の autotune 設定は、移植すると失敗するか遅くなる可能性があります
- **確認すべきこと**
  - SDPA が flash または cuDNN を選んでいるかを確認します
  - 特に逆伝播が math や efficient のバックエンドに落ちていないかを確認します
  - バックエンドは明示的に固定し、ログに記録してください
- **独自 CUDA のビルド**
  - `-gencode arch=compute_120,code=sm_120` を指定します（アーキテクチャ固有の命令を使う場合は `120a`）
  - PTX の JIT フォールバックで起動が遅くなっていないかも確認します

**7. 参照実装の仕様を明文化したファイルがない**

「AdamW」は 1 種類ではありません。diffusion-pipe の作例では `adamw_optimi` が多く使われます（要確認）。これは Kahan 和や decoupled weight decay の扱いが `torch.optim.AdamW` と異なります。

ステップ 1 の成果物として、次の項目を、出典となるコード行付きで仕様ファイルに固定し、実装者に渡してください。

- オプティマイザの種類とハイパーパラメータ
- LoRA パラメータのデータ型（FP32 か BF16 か）
- timestep 分布と、解像度に応じた shift
- 損失の重み付け
- 勾配クリッピングの範囲と、ノルム計算の精度
- キャプション dropout

**8. ComfyUI 互換の検証方法が弱い**

「効果がある」ことの確認だけでは、キーの取りこぼしや倍率の誤りを見逃します。次を必須にしてください。

- 既知の ΔW を持つ合成 LoRA を作り、ComfyUI でパッチした重みが W+ΔW と一致することを確認する
- ComfyUI のログに未適用キー（"lora key not loaded"）が 0 件であることを確認する
- alpha テンソルを保存するかどうかを決め、実効倍率 alpha/rank の解釈を参照実装と一致させる
- 参照実装で学習した LoRA とネイティブで学習した LoRA を、同じシードとサンプラーで ComfyUI 上で出力比較する

### 中

**9. キャッシュの境界が未定義**

- **データ拡張との衝突**
  - タグのシャッフルやキャプション dropout を使うと、テキスト条件の事前計算は成り立ちません
  - Qwen3-0.6B は軽量なので、オンラインで計算しても大きな負担にはなりません
  - 反転やランダムクロップを使う場合は、潜在表現を変種ごとにキャッシュする必要があります
- **LLM adapter**
  - adapter を LoRA の対象にする場合、adapter の出力はキャッシュできません
  - adapter の入力が Qwen の隠れ状態だけか、別のトークン列も使うかを確認してください（要確認）
- **VAE の精度**
  - VAE を FP32 で通すか BF16 で通すかで、潜在表現がずれます
  - キャッシュ作成時の精度も仕様ファイルに含めてください

**10. バケット、CUDA Graphs、compile の相互作用**

- **CUDA Graphs**
  - グラフは形状ごとに 1 本必要で、バケット数に応じてメモリプールが増えます
  - キャプチャするなら capturable な AdamW を使います
  - 勾配クリッピングで `.item()` を呼ぶとホストとの同期が起き、グラフを壊します
  - 損失ログも数ステップごとに非同期で回収します
- **torch.compile**
  - 形状ごとの再コンパイルを避けるため、dynamic の設定とバケット数の上限を決めます

**11. 測定条件のばらつき要因が未記録**

- **記録する環境情報**
  - 600W 機ではクロックと温度で結果が変わるため、電力、クロック、温度、ECC の状態を記録します
  - 可能なら `nvidia-smi -lgc` でクロックを固定した測定と、固定しない測定の両方を取ります
- **集計方法**
  - 各条件を 3 回以上実行し、ウォームアップ後 200 ステップ以上を計測します
  - 時間は CUDA イベントで計測します
- **総所要時間**
  - コンパイル時間とグラフのキャプチャ時間は、反復時間とは別に計上します
  - 利用者にとっての最終指標である「LoRA 完成までの実時間」も必ず報告します

**12. 成果物の公開と中断時の扱い**

- 成果物は一時ファイルに書き、fsync してから rename で公開します。
- safetensors のメタデータに次を入れます。
  - ベースモデルのハッシュ
  - rank、alpha、ステップ数、データセットのハッシュ
- 中断に備えた再開用チェックポイントと、公開する LoRA は別物として扱います。

### 低：高速化の候補として追加するもの

- **メモリ配置**
  - 96 GB あれば、小規模データセットの潜在表現キャッシュを VRAM に常駐させられます。転送とデータローダーが不要になります。
  - Qwen3 と VAE は、キャッシュ作成後に解放します。
- **LoRA の小行列**
  - 凍結重み W に LoRA の A を出力次元方向で連結し、W と A を 1 回の GEMM で計算する
  - LoRA の加算を GEMM のエピローグに融合する
  - 層を跨いで batched GEMM にまとめる
- **不要な計算の省略**
  - 最初の LoRA 層より上流（patch embed への入力など）では dX を計算しない
- **精度の変更**
  - FP8 や NVFP4 は SM 12.0 で使えますが、品質条件が変わります
  - 採用する場合も「同一精度での比較」とは別の枠で扱ってください

## 修正後の実装順序

1. 参照実装の仕様ファイル、固定入力セット、FP32/BF16 の許容誤差を確定する。
2. 比較構成 (a)、(b)、(c) を作り、nsys でカーネル間の隙間（ホスト律速の割合）を 512 と 1024 で測る。
3. (c) に compile、CUDA Graphs、融合を入れて最適化する。
4. **判断ゲート**：ホスト律速の割合が閾値（例：10%）を超えて残る場合だけ (d) に着手する。超えなければ (d) は不採用とする。
5. DSH への統合、ComfyUI での合成 ΔW 検証、アトミックな公開を実装する。
6. 計画の 6 番目の比較を、比較構成 (a)〜(d) で実施する。
