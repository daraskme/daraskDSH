# Gemma 4 キャプション高速化計画の敵対的レビュー（gpt-6.2-astra、dsh ask openai 経由）

**最初に試すべきは、8 並列ではなく `--cache-ram 0` です。** `@muninshiki` の実ログでは、「前処理と HTTP」に割り当てた約 0.45 秒のうち、約 0.3 秒がすでにサーバー内で経過している例が繰り返しあります。並列化の狙いは正しいものの、先にこの内訳を直さないと、効いていない変更を採用しかねません。

1. **［高］画像ごとに巨大なプロンプトキャッシュを入れ替えている。** `llama.log:163–166` では、スロット選択から起動まで **306 ms** かかり、その間に **669 MiB** のキャッシュを追い出しています。画像は毎回異なり、リクエスト内でも画像が指示文より先です。過去画像の状態を保存する利益は小さい一方、0.3 秒が49回なら約15秒に相当します。全額が回収可能という意味ではありません。  
   **最小修正:** 同じ50枚・`-np 1` で `--cache-ram 0` だけを変え、総時間と `select → launch_slot` の差を比較する。速ければ以後の基準にする。

2. **［高］`-np 8` で8枚分まとめられるのは、主に生成ステップ。** mmproj の重みは一度ロードすればよく、b12469 の GPU オフロードも既定で有効ですが、**異なる画像のエンコードは毎回必要**です。画像処理・prefill がスロット順に進む間は生成も待ち得ます。仮に 0.40 秒が各画像で直列に残れば、生成だけ理想的に8分割しても `7.3 + 50 × (0.40 + 1.1/8) ≈ 34.2 秒`。40秒までの余裕は全体で6秒弱です。これは予測値ではなく、仮定を置いた試算です。  
   **最小修正:** 「0.3〜0.5秒/枚」の予測を削除。前処理込みの同時リクエストを4本→8本と試し、**50枚すべてを保存するまでの実時間**で選ぶ。40秒を切れば16本は試さない。

3. **［高］`-c 8192×並列数` は今回の入力に対して過大。** 実ログは `kv_unified=false`、画像予算は `-ub 512` により **512 token に制限済み**です。たとえば実測447入力＋最大256出力なら703 token。8本に計65,536 tokenを予約しても、その余白で生成は速くならず、KV用VRAMと起動時の割り当てだけが増えます。逆に並列数だけ変えれば、スロット不足で長い入力が壊れます。  
   **最小修正:** 固定50枚でテンプレート込みの最大入力＋256が1,024に収まるなら、8本は `-np 8 -c 8192` から。起動ログの `n_ctx_slot` で確認し、`-ub` は変えない。

4. **［高］2回目以降の比較が「生成ゼロ」で合格し得る。** `pipeline.py:119–130` は既存の非空 `.txt` をスキップし、対象がゼロならサーバーすら起動しません。また元ログでも同じ1スロットの生成が約16 ms/tokenから38〜42 ms/tokenまで落ちる区間があり、109秒を固定の対照値にするのは危険です。  
   **最小修正:** 元データでなく同じ50枚の作業コピーで毎回50件を再生成し、現行 `-np 1` も同じGPU占有条件で取り直す。スロット別 token/s ではなくロード込み総時間を採否に使う。

5. **［高］並列化で最も壊しやすいのは画像と `.txt` の対応。** 完了順の結果を入力順のパスと組み合わせると、長さも英文も正常なまま他の画像の説明が保存されます。平均文字数にも `finish_reason` にも表れません。  
   **最小修正:** ワーカーは元の `(path, text)` を返し、親だけがその `path` に保存して進捗を更新する。固定20枚の目視は、保存後の画像と同名 `.txt` を対にして行う。

6. **［中］「クライアント時間が10%以上ならC++化」は削除。** 8本の HTTP 待ち時間は重複し、そこにはサーバーの待ち行列も含まれます。各要求で10%以上を占めても、GPUがすでに埋まっていれば、直リンクで短縮できる総時間はほぼゼロです。逆に直接呼び出しを1枚ずつ実装すれば、生成バッチの利益を失います。  
   **最小修正:** 今回はネイティブ化を計画から外す。PIL→JPEG→HTTP を同じワーカーに入れるだけにし、「前処理を重ねる」も独立施策として数えない。

7. **［中］896 px化は、速度を改善せず品質だけ落とし得る。** 同じ視覚token数でも、縮小で消えた文字や細い装飾は戻りません。一方、画像エンコードが律速なら、送信JPEGの寸法より **実際に処理する視覚token数** の方が直接的なレバーです。  
   **最小修正:** 896 px案は削除。40秒に届かず画像処理が詰まった場合だけ、1024 pxのまま既存の `--image-max-tokens` で実token数が減る値を1点試し、固定20枚で細部の欠落を見る。FAも既定の `auto` ですでに有効なら比較不要。

**判定：修正後に着手可。**
