# Gemma 4 キャプション生成の高速化計画

方針: **速度 ≥ 品質**。キャプションの文面（モデル、プロンプト、temperature 0.2、最大 256 token）は変えない。最小の変更で最大の短縮を取る。新しい抽象化や設定項目は、測定で必要と分かるまで追加しない。

## 現状（2026-11-19 実測、50 枚、`@muninshiki` ジョブの llama.log）

- 構成: `plugins/lora-training/pipeline.py` が llama.cpp b12469 の `llama-server` を `-np 1 -c 8192 -ngl all --reasoning off` で起動する。画像を 1 枚ずつ、PIL で 1024px の JPEG にしてから base64 にし、HTTP の `/v1/chat/completions` で送る。
- モデル: gemma-4-Ortenzya 31B Q4_K_M（18.7 GB）と mmproj BF16（1.2 GB）。GPU は RTX PRO 6000 Blackwell（96 GB）。
- 時間（50 枚で約 109 s）:
  - モデルのロード: 7.3 s
  - 1 枚あたり約 1.97 s
    - プロンプト評価（画像込みで 384 token）: 0.40 s
    - 生成（約 70 token、16 ms/token = 62 token/s）: 1.1 s
    - 残り約 0.45 s は、クライアント側の前処理と往復
- 律速: 生成が 1 本の流れ（バッチ 1）。1 token ごとに 18 GB の重みを読むメモリ帯域律速なので、同時に処理する本数を増やしても 1 token あたりの時間はほとんど伸びない。

## 打ち手（Astra のレビューを反映。1 段ずつ測り、速くならなければ捨てる）

レビュー全文: [gemma-caption-astra-review.md](gemma-caption-astra-review.md)

1. **`--cache-ram 0`** — 画像ごとに約 670 MiB のプロンプトキャッシュを追い出しており、1 回あたり約 0.3 s かかっている。画像は毎回違うので、キャッシュしても得がない。`-np 1` のままこれだけを変えて測る。
2. **並列スロットと同時リクエスト** — `-np 4` と `-np 8` を試す。`-c 8192` は全体の値で、スロットあたり 1,024 token に収まることを起動ログで確認する。前処理（PIL → JPEG → HTTP）は各ワーカーの中で行う。ワーカーは `(path, text)` を返し、ファイルへの書き込みと進捗の更新は親だけが行う。40 s を切ったら 16 並列は試さない。
3. **画像のトークン数**（40 s に届かず、画像処理が詰まっている場合だけ）— 1024px のまま `--image-max-tokens` を 1 点だけ試し、固定 20 枚で細部が欠けていないかを確認する。

削除した項目: 「1 枚あたり 0.3〜0.5 s」という見込み、`-c 8192×並列数`、C++ への置き換えの判断（並列時は HTTP の待ちが重なるので短縮できない）、896px への縮小、flash attention の比較（既定の auto で有効）。

## やらないこと

- モデルの変更、より低いビット数への量子化、投機的デコード、サーバーの常駐、独自カーネル、プロンプトの変更、C++ への置き換え

## 品質の確認

- 固定の 20 枚で、保存後の画像と同名の `.txt` を対にして目視で確認する（並列化で画像とキャプションの対応がずれていないか）。
- 途中で切れたキャプションが 0 件であること。

## 計測

- 同じ 50 枚の作業用コピーで、毎回 50 枚すべてを作り直す。現行の `-np 1` も同じ条件で測り直す。比較は「ロード込みで 50 枚の保存が終わるまでの実時間」で行う。

## 完了条件

- 50 枚のキャプション付けが 109 s から 40 s 以下になる。
- 品質の確認を通ったら、旧経路（1 枚ずつ処理するコード）を削除する。

## 結果（2026-11-19、`@muninshiki` の 50 枚の作業用コピー、毎回 50 枚すべてを作り直し）

| 構成 | 総時間（ロード込み） | 1 枚あたり | 平均文字数 |
|---|---:|---:|---:|
| A: 従来（`-np 1`、キャッシュあり） | 91.1 s | 1.67 s | 279 |
| B: `-np 1` + `--cache-ram 0` | 78.4 s | 1.40 s | 278 |
| C: 4 並列 | 52.9 s | 0.89 s | 288 |
| D: 8 並列 | 45.0 s | 0.72 s | 285 |
| E: 16 並列 | 39.5 s | 0.64 s | 284 |
| F: 8 並列 + `--image-max-tokens 256` | 39.7 s | 0.62 s | 290 |
| **G: 16 並列、スロットあたり 1,024 token（採用）** | **39.6 s** | 0.64 s | 283 |

- 8 並列では、1 スロットあたり 77.6 ms/token。全体の処理量は 1 本のときの約 1.7 倍にとどまった。原因は、他のスロットの画像の prefill（中央値 0.6 s、最大 2.8 s）が同じバッチに入って計算律速になり、生成が止まること。
- 画像トークンを 256 に絞った F は、16 並列と同じ速さだった。品質を下げずに済む 16 並列を採用した。
- `-np 16 -c 8192` ではスロットあたり 512 token になり、長いキャプションが途中で切れる。そのため `-c` は「1,024 × 並列数」にした。
- 品質: A と G を同じ画像ごとに比べると、内容（髪色・服装・ポーズ・場面）が一致しており、画像とキャプションの対応もずれていない。途中で切れたキャプションは 0 件。
- 旧経路（1 枚ずつ処理するコード）は `pipeline.py` から削除した。
