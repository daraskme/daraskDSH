# 並列数の調査と運用設定

確認日: 2026-11-18 JST

全体統括はサブスク認証のCodex CLIを使う Astra 6.2（`gpt-6.2-astra`、effort `high`）に固定し、通常タスクはCursor・Grokに振り分ける。Astraへ通常タスクを新規割当しない。Devinは担当から除外する。Cursor/Grokが解決できないものは Astra 6.2 → Claude Opus 5.5（`claude-opus-5-5`、effort `high`）へ引き継ぐ。

## 公開情報と実測

| サービス | 確認した仕様 | この環境での確認 |
| --- | --- | --- |
| Cursor CLI | 公式に複数CLIの並列動作をサポート。CLIアカウント別の最大同時数は確認できない。画面上の「8エージェント」とCLIの上限は別 | Ultra、CLI `2026.11.13-eacade1`。短いツールなしの呼び出し4件同時に成功 |
| Grok Build | 公式ソースの `max_concurrent` 既定値は32。これは内部サブエージェントの枠であり、別プロセスのCLIや契約枠の最大値ではない。`sampling_limit` は別の設定 | CLI `1.0.88`。Cursorの4件と同時に、Grokも4件成功 |

## 最大モード

固定の3枠は廃止。総枠は `min(CPU並列数×2, 起動時の空きメモリ÷2GiB, 128)` で計算する。調査時の端末は24論理CPU・空きメモリ約108GiBで、**総枠48**。これはDSHの運用上限であり、提供元の契約上限ではない。

枠はワークスペースのキュー単位。DSH本体の子エージェント上限は128に設定し、その内側で上記の制御を行う。本体設定でさらに低い値を指定した場合は低い方を採用する。Astra統括・通常Cursor/Grokのみの構成で、テスト用CLIによるDSH本体の統合検証は32タスクを完了し、テスト上限の同時実行16件を確認した。通常Astraへの割当がないこと、未解決分のAstra→Opus引き継ぎ、旧通常Astraの中断・確認待ち履歴の保持も検証した。これは実サービスの契約上限の実測ではない。

Cursor/Grokは各4枠から開始し、タスクの応答成功ごとに1枠ずつ増やす。429等の制限エラーでは該当サービスの枠を半分に減らし、複数回の成功後に拡大を再開する。該当タスクは指定されたAstra→Opusの順へ引き継ぐ。利用枠切れと明示されたサービスは現在の実行中は新規割当を止め、他の通常担当を使う。Astraも利用枠切れの場合は、引き継ぎ時にもその枠を使わずOpusへ進める。利用枠を回避するために認証やアカウントを切り替える処理はない。

**引き継ぎ先として動くAstra/Opusの子タスクは合計1枠**とし、総枠の内数にする。Astraの子は引き継ぎ専用であり、Codexの子タスク枠は1に固定する。親の計画・レビュー用呼び出しは別。依存関係、実行中・確認待ちの読み書き範囲が重なるタスクは枠が空いていても同時に動かさない。

サービス既定のCursor/Grokモデル・オプションは初回割当時に保存する。Astraは統括・引き継ぎ担当とも `gpt-6.2-astra`、effort `high` に固定し、Codex CLIのサブスク認証を使う。旧Devin担当および旧通常Astra担当の未着手・中断作業は、試行記録を保持してCursor/Grokへ再割当する。確認待ち・受入済みの成果は保持する。担当順を更新しても過去の試行・証拠・受入記録は消さない。並列枠・エラー・履歴は `task_queue` の `status` で確認できる。

必要ならサービス環境変数で運用上限を指定する（いずれも1〜128）:

| 環境変数 | 既定 |
| --- | --- |
| `DSH_TASK_MAX_PARALLEL` | 上記のCPU・メモリ計算値 |
| `DSH_TASK_CURSOR_MAX` | 総枠と同じ |
| `DSH_TASK_GROK_MAX` | 総枠と同じ |

再起動後は自動で実作業を再開しない。`status`で中断記録を確認して`run`すると同じ段階から再開する。`run`は利用枠切れによる割当停止も解除するので、枠が戻る前に繰り返さない。
