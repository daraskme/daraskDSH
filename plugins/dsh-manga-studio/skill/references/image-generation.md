# 画像生成への受け渡し

- いつ読むか: ネームが固まり、画像生成モデルで作画するとき。プロンプトや krea_layout_v1 の JSON を書き出すとき。生成した絵で人物が揺れる・読み順が崩れる・文字が化けるとき。
- いつ読まないか: 企画・ネームの段階（絵の都合でネームを曲げない。先に `story.md` `paneling.md`）。

出典の詳細は `docs/dev/research-1-ai-manga-pipeline.md`。ここに書くモデルの性能は 2026-11 時点の報告で、変わる。確かめた日付のない数値は使わない。

## 1. 分担を先に決める

公開されている実践談の多くは、同じ分担に落ち着いている。LLM が構成・コマ割り・台詞・コマごとのプロンプト、画像モデルが作画、人間（または道具）が配置・写植・仕上げ（aipicks 2026-04、Qiita yongyong 2026-01、note eriqaamy 2026-01）。このスキルでも同じに分ける。

| 工程 | 誰が | このスキルの成果物 |
|---|---|---|
| 企画・筋・ネーム | LLM（このスキル）と作者 | `name/epNNN.toml`、`renders/epNNN.md`、ネーム画像（`name_render.py --html`） |
| 人物の固定 | 作者が決め、画像モデルでキャラシートを作る | `characters/cast.toml` の `appearance`・`reference`、領域別 LoRA の別名 |
| 作画 | 画像モデル | `name_export.py` の書き出し（krea / panels / page-prompt） |
| 写植 | 道具（CLIP STUDIO、Canva など）か画像モデル | `name_export.py --to lettering` の CSV |
| 検品 | 別の目（`visual-check.md`） | 検品メモ |

「設計 8 割、生成 2 割」という報告がある（note note_ai_s 2026-03）。ネームで決めていないことを、生成のたびに画像モデルに決めさせると、コマごとに違う答えが返る。

**画像を生成していないのに、生成した・確認したと書かない。** このスキルの成果物はネームとプロンプトで、絵の出来はモデルを回してみるまで分からない。

## 2. 生成の単位を選ぶ

| 単位 | 向く場面 | 弱み | 書き出し |
|---|---|---|---|
| コマ 1 枚ずつ → 合成 | 人物の一貫性、構図の制御、修正のしやすさを優先するとき | 合成の手間。コマの外の空気（間白、はみ出し）は手で作る | `--to panels` |
| ページ一括（自然文で配置を指定） | 参照画像を多く取れるモデル（Nano Banana Pro など）で手早く見本を作るとき | 読み順・コマ数・人物の左右が崩れやすい | `--to page-prompt` |
| ページ一括（bbox で配置を指定） | 配置を学習したモデル（krea_layout_v1 の LoRA）を使うとき | 対応モデルが要る。配置の推定は叩き台なので確かめる | `--to krea` |

ページ一括は手軽だが制御が効きにくく、コマ別生成と合成が最も実用的という報告がある（note note_ai_s 2026-03）。一方、配置を設計図のように書けばページ一括でも通るという報告もある（Anifusion 2025-11）。迷ったら、扉や見せ場の 1 ページだけ一括で試し、崩れたらコマ別に切り替える。

## 3. 文字を画像に描かせるか

| 方針 | `--text` | 向くとき | 注意 |
|---|---|---|---|
| 吹き出しだけ描かせて、後で写植 | `blank`（panels / page-prompt の既定） | 商業の体裁、長い台詞、誤字が許されない | 吹き出しの数と大きさをネームで決めておく。写植は `--to lettering` の CSV から |
| 画像に日本語を描かせる | `in-image`（krea の既定） | 日本語の文字を学習したモデル、短い台詞、擬音 | 誤字・縦書きの崩れ・読み順の入れ替わりを検品で必ず見る |

日本語の文字を最もよく描けるとされるモデルでも、台詞に誤字や崩れが出て手で直している報告がある（Qiita yongyong 2026-01）。崩れたら吹き出しを大きくして再生成する手（ai-souken 2025-11）、ナレーションに縦書きを明示しないと横書きになる報告（Qiita KLaboratory 2025-12）もある。台詞の正確な文字列は画像の外（ネームと写植の一覧）で管理し、画像に描かせた文字は「写植の下描き」として扱うのが安全。擬音・描き文字は絵の一部なので、画像に描かせる価値が高い。

## 4. 人物を揺らさない

崩れの原因と対策の報告をまとめると、効くのは次の操作（note rich_emu7600 2026-09、aipicks 2026-07、note note_ai_s 2026-03）。

1. **画風ブロックと人物ブロックは全コマ同じ文面。** 変えてよいのは構図・表情・動作・背景（ネームの `shot` `angle` `pose` `expression` `visual`）だけ。`name_export.py` はこの順で組み立てる。言い回しを途中で変えると別人になる。
2. **外見は項目ごとに書く。** 年齢層、体格、髪（色・長さ・形）、目、服（色・形）、小物。`cast.toml` の `appearance` に 1〜2 行で。服は固定の文面にし、着替えの回だけ `outfit_en`。
3. **キャラシートを先に作り、毎回オリジナルから渡す。** 三面図と表情集。前のコマの出力を次の参照にしない（伝言ゲームで少しずつずれる）。参照にない角度（真後ろ、真上）は、別に参照を作るか、そのアングルを避ける。
4. **強い表情語を弱める。** 顔が崩れたら「大笑い」を「口角を上げる」程度に。漫符で感情を足せば、顔を壊さずに済む（`manpu.md`）。
5. **人数と位置を明示する。** 「このコマの人物はちょうど 2 人」「A が右、B が左」を絶対位置と相対位置の両方で書く（Qiita KLaboratory 2025-12）。`--to panels` は `Exactly N characters` と左右を書き出す。
6. **場所の言い回しも固定する。** 同じ場所は毎回同じ文面（`place_en`）で。指定しなかった小物はコマごとに変わる。
7. **吹き出しと擬音の置き方を書く。** 吹き出しは話者の頭の上（実際の漫画で、台詞の文字の中心が話者の顔より上なのは 72%）、先に話す人を右に（90%）。画面外の声はしっぽを枠の外へ、ナレーションは角の四角い箱。擬音は縦書きが 83%、4 割は斜めで、擬音の矩形が人物の体の枠と重なるのが半数（`corpus-norms.md` §7）。人物に重ねるかは演出で決める。`--to panels` は台詞の種類ごとに置き場所を英語で書き出す。
8. **描き込みの段階をコマごとに渡す。** `detail`（決め・通常・簡略）と `background` は、`--to panels` と `--to page-prompt` で英語の指示になる。決めコマだけ人物と背景をきちんと描かせ、ほかは線を減らす。全コマに同じ「高品質」の語を付けると、全コマが一枚絵になる（`art-direction.md`）。
9. **キャラシートも白黒の線画で。** 参照画像が厚塗りだと、コマも厚塗りになる。

参照画像の扱いはモデルで違う（2026-11 時点の公開情報）:

- Nano Banana Pro: 参照画像は最大 14 枚、同一性を保てるのは最大 5 人と公式発表（Google 2025-11-20）。登場人物が 5 人を超えるページは、コマ別生成に切り替える。
- Midjourney V7: `--oref`（Omni Reference）が `--cref` の後継。
- NovelAI の Vibe Transfer: 画風・色の転写が主目的で、人物の固定用ではない。
- Stable Diffusion 系: 人物ごとの LoRA と ControlNet（openpose / scribble）でコマごとに生成し、inpaint で直す流れが古典的（scrapbox motoso）。
- 学習なしで揃える研究（StoryDiffusion、DiffSensei、MangaDiffusion）もあるが、台詞と話者の対応づけや空間の一貫性に弱いと指摘されている（TaleDiffusion 2025-09）。

## 5. krea_layout_v1（JSON / BBOX で配置を指定する）

`name_export.py --to krea` は、ページごとに次を書き出す。

- `pNNN.layout.json`: 絶対ピクセル xyxy の layout（保存・編集用）
- `pNNN.prompt.txt`: `krea_layout_v1 ` に、座標を 0〜1000 に正規化した JSON を続けたプロンプト（学習・推論用）
- `prompts.jsonl`: 全ページのプロンプト
- `character_adapters.json`: 人物表に `lora` がある人物の、領域別 LoRA の設定の雛形（パスと強度は作者が埋める）

項目の対応:

| ネーム | krea の項目 |
|---|---|
| コマ | `panels[]`（`id` は p1, p2…、`reading_order` は配置から計算した読み順） |
| 人物 | `label: character`、`character_id`（人物表の ID）、`lora`（別名）、`caption`（appearance＋表情）、`pose` |
| 吹き出し | `label: object`、`kind`（`speech_balloon` `shout_balloon` `thought_balloon` `narration_box`）、`id: balloon_N` |
| 台詞 | `label: text`、`kind: dialogue`（モノローグ・ナレーションは `narration_box`）、`text`（行を全角空白でつなぐ）、`balloon_id`、`speakers`（話者の `lora` 別名。話者がそのページに描かれているときだけ） |
| 擬音 | `label: text`、`kind: sound_effect` |
| 漫符・効果 | `label: object`、`kind` は `manpu.json` の `krea_kind`（集中線 `focus_lines`、汗 `sweat_drops` など。対応する kind が無い記号は `emotion_mark`）、`caption` は英語の記述 |

注意:

- 配置（人物・吹き出し・漫符の bbox）は推定の叩き台。人物の左右（`pos`）と吹き出しの順は守るが、顔の位置までは知らない。重要なコマは `box` で固定する。
- `--krea-repo <krea2_layout のあるディレクトリ>` を付けると、そのリポジトリの `validate_layout` でも検査する。内蔵の検査は同じ規則の写し。
- プロンプトが長いと、学習・推論の最大トークン長を超えることがある。項目の多いページ（人物 5 人以上、吹き出し 12 個以上）は、コマ数か漫符を減らすか、コマ別に生成する。
- 領域別 LoRA は、領域どうしを重ねないほうが安定し、マスクした LoRA は通常より強い強度が要ることが多いという報告がある（Krea 2 向け ComfyUI ノードの README）。人物の箱が重なるコマは、`box` で離すか、手前の人物だけに LoRA を当てる。
- **PH3DaraskMix の manga lora**（JSON BBOX・漫符の LoRA）は同じ JSON で、接頭辞が `ph3_layout_v1 `、座標は 0〜1000 の整数、`character_id` を書かない（人物は `lora` 別名で結ぶ）。`name_export.py --to krea --layout-prefix ph3` で書き出す。漫符は、manga lora の語彙と同じ 108 のキーを、18 種類の kind と英語の caption の組に直して書き出す（専用の kind が無い記号は `emotion_mark` ＋ caption）。学習例の少ない記号（ぐるぐる目、ハート目、汗ばみ）は出にくい。
- `rating = "adult"` の作品の書き出しも同じ形式。成人向けの記号は `manpu.json` で `rating: adult` が付いている。登場人物は全員成人で、人物表の `appearance` にもそれが分かる記述を入れる。

## 6. コマ別・ページ一括のプロンプト

`--to panels` は、画風ブロック → 人物ブロック → コマごとの節（カメラ、場面、場所、人数、各人物の位置・ポーズ・表情・漫符、効果、背景、吹き出し）の順に書き出す。コマの縦横比も添えるので、生成サイズをコマに合わせる（正方形の既定のまま生成すると構図が崩れるという報告がある。note eriqaamy 2026-01）。

`--to page-prompt` は、ページ全体の縦横比、コマ数、「右から左、上から下」の読み順、各コマの位置（ページに対する百分率）と中身を書き出す。読み順は強調しても崩れることがあり（Qiita yongyong 2026-01、nomu-papa 2026-04）、崩れたページは手で並べ替えるか、コマ別に生成する。

どちらも、出力を見て直したことは `renders/` に残す（どのコマを何回、どう直したか）。

## 7. Darask AI Studio から使う

Studio には、このスキルを使うプラグインがある。

- 「ネームを作る」（`manga-name`）: ローカル LLM で計画 → 1 ページずつネーム → 検査で引っかかったページを 1 回直す → ネーム（`--to sections` の見出しと、直せる TOML、検査結果）・台本・ネーム画像（PNG）を保存。
- 「ネームを検査・書き出す」（`manga-name-check`）: 手で直したネームを検査し、同じ成果物を作り直す。
- 「ネームどおりにページを組む」（`manga-name-page`）: `--to compose` の配置どおりに、コマの絵を切り抜いて並べ、フキダシ（楕円・叫び・心の声・ささやき・ナレーション）・擬音・欄外の小文字を描く。

`sections` の `dialogue-p1`〜 はファイルの中のページの順（1 から）で、ページ番号ではない（`pages` の見出しに対応がある）。「漫画のページを組む」（`manga-page`）に渡すと、コマ割りは manga-page の決まった形になり、心の声・欄外の小文字は入らない（`notes` に一覧が出る）。ネームどおりに組むなら `manga-name-page` を使う。

## 8. 生成の前に確かめること

- [ ] `name_lint.py` の指摘（FAIL・WARN）をすべて確かめて処置した（誤りは直し、誤検出や意図した演出は keep と理由を残した）。構造の FAIL（E 群）が残っていると書き出しが止まる
- [ ] 人物表の全員に `appearance` がある（X02）。キャラシートの画像がある
- [ ] 画風ブロックに、実在の作家名・作品名・キャラクター名が入っていない（`formats.md` §3）
- [ ] 各コマの `detail` と `background` を決めた（決めコマは 1 ページに 0〜1 個。背景を描くのは場面の頭と決めコマ。`art-direction.md`）
- [ ] 画風ブロックと negative が白黒の四値（線・ベタ・トーン・白）になっている。キャラシートも線画
- [ ] 文字の方針（in-image / blank）を決めた
- [ ] 生成するサイズ（ページ・コマの縦横比）を決めた
- [ ] プロンプトと生成の記録を残す場所を決めた（`renders/epNNN/`）

生成した後は `visual-check.md` で検品する。Pillow があれば `scripts/tone_check.py` で灰の塗りを測る。
